# 命名规则修复

依据《合同审批附件自动归类_需求文档.docx》第 3 节。保留用户确认的“项目号_文件分类”外层目录与五个业务分类。

| 场景 | 修复后的行为 |
| --- | --- |
| 同一时间上传采购合同、付款凭证、箱单 | 按附件列表顺序编为 1、2、3，不按文件名排序 |
| 后续删除其他类型或补入更早的历史附件 | 已保存编号不变，新类型追加编号 |
| 原类型新增第二份不同文件 | 主序号不变，形成 2-1、2-2；已用子号不复用 |
| 采购合同A.pdf 后续仍上传采购合同A.pdf，内容修改 | 原编号不变，系统自动生成“序号-采购合同v2-项目号.pdf”，只保留最新版 |
| 上游提供相同 document_id | 可关联改名后的修订，不必提供 revision，物理 UUID 不替代 document_id |
| 同一批包含多份同名文件，或历史存在多个独立同名文件 | 分别编号保留，避免无法消除的同名歧义 |
| 已归档 v3 后重传系统记录过的旧内容 | 历史最新版仍保留，不回退版本 |
| 后续流程仅上传新增/修改文件 | 从磁盘历史记录合并有效归档，其他历史文件保留，不要求重新上传 |
| 首次升级已有目录 | 从旧清单继承编号，之后使用编号记录.json |
| 实际保存失败或仅预览 | 不提交新的编号记录 |
| 不同采购单位 | 可配置命名模板、类型显示名及允许类型白名单 |

“主序号按上传顺序”与“后续编号不变”采用以下优先级：第一次编号使用现有上传时间与列表顺序；实际保存后编号固定，随后补入早期材料也不重新打乱历史序号。同一类型从一份变为多份时允许增加子编号，原主号不变。

本地历史下载目录不含原附件数组次序时，使用现有输入顺序。版本管理采用同项目、同类型、同基础名的后续提交关系及内容哈希变化自动递增，不要求经办人标 v2/v3；完全改名且无逻辑文件 ID 时按新增文件处理。同一批多个同名文件仍分别保留。文件名中自带的 vN 不控制系统版本数字。

默认中标合同文件名按文档示例使用“中标合同”，分类仍保留“中标合同（内贸）”。其他类型保留区分用途所需的名称，可通过采购单位 type_labels 配置简写。

代码修改不会修改已保存目录；部署新代码并重启服务后，重新分析、保存才生效。测试使用隔离的临时目录，不改动真实附件。
